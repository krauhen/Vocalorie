## ADDED Requirements

### Requirement: Search suggestions appear only during active search
The system SHALL display saved meal search suggestions in the meal capture overlay only when the search query is non-blank (`searchQuery.isNotBlank()`). When the search input is empty or contains only whitespace characters, the suggestions list SHALL NOT be displayed.

#### Scenario: Suggestions hidden when search query is empty
- **WHEN** the user opens the meal capture overlay and the search input field is empty
- **THEN** no saved meal suggestions are rendered

#### Scenario: Suggestions displayed when query has non-blank text
- **WHEN** the user types "Apfel" into the search field
- **THEN** matching saved meals are displayed as suggestion cards

### Requirement: Search suggestions paginate in increments of 5 up to configurable limit N
When displaying search suggestions, the system SHALL render them in a scrollable list starting with an initial page of 5 items. When the user reaches the end of the scrollable list, the system SHALL load 5 additional matching items per pagination step until reaching either the total number of matching meals or the maximum limit N. If the total number of matches is less than the current page limit, all available matches SHALL be displayed.

#### Scenario: Initial search displays first 5 matches
- **WHEN** the user enters a search query that matches 18 saved meals
- **THEN** exactly 5 suggestion cards are initially visible in the list

#### Scenario: Reaching list end loads next 5 matches
- **WHEN** the suggestions list displays 5 items and the user scrolls to the bottom
- **THEN** 5 more items are appended, displaying 10 items in total

#### Scenario: Pagination halts at configurable maximum limit N
- **WHEN** the maximum limit N is configured to 20 and the search matches 45 meals
- **THEN** successive scrolling stops loading after reaching 20 items

#### Scenario: Total matches fewer than page size
- **WHEN** a search query matches 3 saved meals
- **THEN** all 3 meals are displayed with no additional items to paginate

### Requirement: Search suggestion limit N is configurable in settings defaulting to 50
The system SHALL provide a setting in the settings screen allowing the user to configure the maximum search suggestion limit N. The setting SHALL enforce a minimum of 5 and a maximum of 50, defaulting to 50. Any entered value exceeding 50 SHALL be clamped to 50.

#### Scenario: Default suggestion limit is 50
- **WHEN** the app runs with default settings
- **THEN** the search suggestion limit N is 50

#### Scenario: Configured suggestion limit is applied to search
- **WHEN** the user updates the search suggestion limit to 15 in Settings and saves
- **THEN** subsequent searches paginate up to a maximum of 15 suggestions

#### Scenario: Entered values above 50 are capped at 50
- **WHEN** the user enters 75 into the search suggestion limit setting
- **THEN** the saved value is clamped to the maximum allowed limit of 50

### Requirement: New meal drafts provide an editable timestamp picker prior to saving
The system SHALL render an editable timestamp field (`EntryTimestampField`) directly in the meal draft review editor for all new meal drafts before saving, including drafts generated by LLM estimation and drafts prepared from cache or search reuse. The draft timestamp SHALL be initialized to the target entry timestamp corresponding to the active day offset. The user SHALL be able to modify both date and time using pickers or manual text input, and the modified timestamp SHALL be persisted when the meal is saved.

#### Scenario: New estimate draft displays timestamp prefilled with target day
- **WHEN** a new meal estimate finishes while viewing yesterday (day offset 1)
- **THEN** the draft editor displays the date/time picker pre-filled with yesterday's date at the current time

#### Scenario: Cache-reused draft displays timestamp prefilled with target day
- **WHEN** a cached meal or search suggestion is selected for reuse
- **THEN** the draft editor displays the date/time picker pre-filled with the active target day timestamp rather than the historical meal's creation date

#### Scenario: Saving a draft preserves user-edited timestamp
- **WHEN** the user adjusts the draft date/time to 3 hours earlier and taps "Save entry"
- **THEN** the new meal is saved to the database with the user-selected timestamp

#### Scenario: Malformed timestamp disables saving
- **WHEN** the user types an unparseable date/time into the draft's timestamp field
- **THEN** the field indicates a parse error and the "Save entry" button is disabled until corrected
